Two caches that were blind to a language, and a release that publishes itself
to the MCP Registry. Nothing stored changed shape, and the two fixes correct
themselves on upgrade rather than asking for a pass.

- **A Rust entry never invalidated, so the cache served facts from source that
  had been edited away.** `isFingerprintedSource` listed nine extensions across
  four languages and `.rs` was not one of them, and neither `Cargo.toml` nor
  `Cargo.lock` was a manifest it knew. A Rust unit adds its workspace root as an
  input tree, so the walk matched no file at all and hashed the empty string —
  `e3b0c442…b855`, the same constant for every crate, before and after every
  edit. Editing a `.rs` file therefore invalidated nothing.
- **No reindex is needed, and the reason is worth stating rather than trusting.**
  The stored fingerprint was the hash of nothing; the one this build computes is
  the hash of the crate. They differ, and a fingerprint that does not match is
  never taken for a hit, so the stale entry falls out on the first pass after
  the upgrade and the facts are produced again from the source that is actually
  there.
- **The extensions now come from `config.SourceExtensions` over
  `SupportedLanguages`**, so a language the configuration accepts cannot be one
  the cache is blind to. `Cargo.toml` and `Cargo.lock` join the manifests, and
  the empty-tree hash is asserted by name so a tree that matches nothing cannot
  pass quietly again.
- **The watcher had the same shape of bug, in the other direction.** `isSource`
  carried its own switch and knew Go, TypeScript and Rust, so a repository
  declaring **Python or Dart** — both of which this build indexes — had every
  source file skipped by the reconciliation scan. No change to a `.py`, `.pyi`
  or `.dart` file was ever a change the reconciler could see, and nothing asked
  for a reindex on one. The two bugs are siblings: the watcher missing a
  language means no reindex is asked for, and the cache missing one means a
  reindex that runs answers from a stale entry.
- **Both tables now live beside the `SupportedLanguages` that decides what a
  configuration may declare**, and `internal/agenthook` — which carried a third
  copy and disagreed with the first — reads it too. A new accepted language
  arriving with no files is what the old bug looked like, and a test now refuses
  it. The aliases are keys of their own: a configuration saying `py` is as valid
  as one saying `python`.

**Kivgraph is now published to the official MCP Registry** as
`io.github.Luqueee/kivgraph`, from the release itself.

- **Each release carries a second archive, `kivgraph-<os>-<arch>.mcpb`.** The
  registry accepts `npm`, `pypi`, `nuget`, `cargo`, `oci` and `mcpb` packages,
  and a `.tar.gz` is none of them; four of the five alternatives would mean
  distributing Kivgraph a second way rather than describing the way it already
  is. Nothing is built twice — the `.mcpb` packages the same bundle directory,
  so the binary inside it is the same file, byte for byte, and both archives are
  attested.
- **The MCPB manifest runs `server/bin/kivgraph serve`**, which is the command
  `kivgraph mcp install` already writes into a client configuration. Installing
  the bundle and installing the binary run the identical process.
- **The bundle is nested under `server/` rather than flattened**, because it
  already carries its own `manifest.json` — the provenance one — and flattening
  would put two different files at one path with one winning in silence. It also
  keeps the relative `RUNPATH` intact: the binary finds `lib/liblbug.so` beside
  itself, so the tree has to move as a unit.
- **The archive is reproducible**, because a `fileSha256` published to the
  registry stops describing anything otherwise. Two runs over one bundle produce
  the same digest, the extracted binary reports its version — which is what
  proves the relative `RUNPATH` survived packaging — and answers `initialize`
  and `tools/list` with its twelve tools over stdio.
- **One limitation is carried rather than hidden.** A registry package has no
  field saying which platform it is for, so both platforms are sibling packages
  and only `compatibility.platforms` inside each archive distinguishes them. A
  client that picks the wrong one gets a binary that will not execute; there is
  nowhere in the current schema to prevent that, and shipping a single platform
  to sidestep it would be worse.

The benchmark harness also stopped reporting a maximum as a percentile.
`find_cross_repo_consumers` failed a release at `11,6 ms` and a pull request at
`5,6 ms` against a `5 ms` limit, and neither number was a `p95`: the tests
measured twenty calls in total and that operation is ten per cent of the
workload, so the figure was the worse of **two**. At two thousand calls the
worst `p95` over fifty runs on a machine held at a load average near `37` is
`0,067 ms`, and the median is `0,048 ms` — the limits were never tight, only the
tail of a two-sample maximum was.
